Executive summary — how a submission is made and entered

  1. Generate (2026-10-20 relay-fix session): restore pinned mirrors (scripts/restore_data.py), run the preregistered gate (scripts/run_relayfix_20261020.py gate), then the Exp2b transfer arm (scripts/run_exp2b_transfer.py gate + emit), which writes submissions/h69-transferonly-<dots>-<stamp>-<sha8>-zeros.tif (all-finite [0,1]) plus a -nan diagnostic twin, with JSON receipts in evidence/.
  2. Validate: the shared template validator (vendor/template66/gems/validate_submission.py) re-reads the bytes from disk and checks CRS EPSG:32611, shape 3730×3292, transform, single band, float32, values in [0,1], and (for the nan twin) NaN only outside the footprint.
  3. Gate: the corridor arm must beat the identical pipeline without corridor priors on the spatially-blocked hide-and-recover holdout (evidence/e2_gate.json), and the registry lane-drift scan must pass (evidence/e3_uniqueness.json). The download banner on the home page is generated from those two files — it cannot say OK unless they do.
  4. Submit: DrivenData competition 306 → New submission → upload the single .tif (or a zip containing exactly one GeoTIFF). It must match the submission format's CRS, shape, and geotransform — ours is written against sample_submission.tif so it matches by construction. Add a short note (≤140 characters) identifying the run, e.g. the receipt note.

Portal error “Predicted values must be in range [0, 1]” — byte-verified causes (2026-10-20): uploading any of these files by mistake triggers exactly this class: (1) labels.tif/existing_faults.tif contain the value −1 in all 7,111,787 outside-footprint cells (int8 nodata); (2) a -nan twin carries 7,111,787 NaN cells, which fail a naive 0 ≤ v ≤ 1 check; (3) training_features.tif carries the −3.4×1038 sentinel. The fix is procedural: upload only the -zeros.tif named on this page (verified all-finite, min 0.0, max 1.0, nodata unset) and re-run scripts/validate_submission.py <file> on the exact bytes before uploading. Portal internals are not observable here, so this identifies the verified byte-level causes consistent with the error, not portal source code.
