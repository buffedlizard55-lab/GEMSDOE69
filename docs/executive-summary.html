Executive summary — how a submission is made and entered

  1. Generate: scripts/run_lane69.py e3 builds the tip graph from the pinned catalogue mirror, emits and scores corridors, places greedy marginal-DTI dots, and writes submissions/h69-relayramp-pullapart-<dots>-<stamp>-<sha8>-zeros.tif (all-finite [0,1]) plus a -nan diagnostic twin, with a JSON receipt.
  2. Validate: the shared template validator (vendor/template66/gems/validate_submission.py) re-reads the bytes from disk and checks CRS EPSG:32611, shape 3730×3292, transform, single band, float32, values in [0,1], and (for the nan twin) NaN only outside the footprint.
  3. Gate: the corridor arm must beat the identical pipeline without corridor priors and the current best on the same spatially-blocked hide-and-recover evaluator. Both uniqueness phases must pass the literal registry rules. scripts/release_gate.py additionally requires artifact-bound holdout, validator, source-manifest and feature-alone canary evidence. Pass flags from another TIFF cannot authorize this file. No download is published while any required evidence is missing.
  4. Submit: DrivenData competition 306 → New submission → upload the single .tif (or a zip containing exactly one GeoTIFF). It must match the submission format's CRS, shape, and geotransform — ours is written against sample_submission.tif so it matches by construction. Add a short note (≤140 characters) identifying the run, e.g. the receipt note.

Known portal error class: “Predicted values must be in range [0, 1]” — caused by artifacts carrying values outside [0,1] (or non-finite cells the portal does not treat as nodata). The -zeros variant avoids non-finite values, but is not authorized for submission unless every gate passes. The -nan variant is diagnostic under our local template policy. Actual portal acceptance requires an organizer receipt; we have not independently reproduced the reported upload error.
